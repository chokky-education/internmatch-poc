# โปรไฟล์นักศึกษาและบริบทฤดูฝึกงาน

สถานะปัจจุบัน: ผู้ใช้อนุมัติ Guided ฉบับแก้และแผนพัฒนาแล้ว นำเข้าระบบจริงบน branch `codex/student-profile-seasons` และตรวจ Local UAT อัตโนมัติแล้ว รอผู้ใช้ลองก่อน PR → CI → Merge → Deploy ข้อความข้อเสนอต่อไปนี้เก็บเป็นบันทึกการออกแบบเดิม; รายงานผลปัจจุบันอยู่ที่ `docs/uat/2026-11-13-student-profile-local-uat.md`

## เป้าหมายที่ผู้ใช้ยืนยันแล้ว

1. ใช้ข้อมูลโปรไฟล์ให้พี่ฝึกงานตอบตามบริบทของนักศึกษาและช่วยติดตามวันสำคัญ ไม่ได้มีไว้แสดงบนการ์ดเพียงอย่างเดียว
2. เริ่มใช้แอปได้ทันทีโดยไม่ต้องกรอกโปรไฟล์ให้ครบ และทยอยขอข้อมูลเมื่อจำเป็นต่อสิ่งที่ผู้ใช้กำลังทำ
3. ข้อมูลนักศึกษารุ่นแรก: ชื่อที่อยากให้เรียก มหาวิทยาลัย คณะ สาขา ชั้นปี และสายงานที่สนใจ โดยเว้นข้อมูลที่ยังไม่ทราบได้
4. ต้องรองรับประวัติแยกตามฤดูฝึกงานตั้งแต่ขอบเขตนี้ ผู้ใช้ไม่ได้เลือกข้อเสนอที่ดูแลเพียงรอบปัจจุบัน
5. ต้องการระบบเพิ่มยศ/เลื่อนยศด้วย ผู้ใช้เรียกว่า “Game theory”; ผู้ช่วยเสนอคำว่า Gamification เพื่ออธิบายกลไกดังกล่าว ยังไม่ได้ตกลงวิธีให้คะแนนหรือเลื่อนยศ
6. ให้ค้นคว้าเรื่องวันสำคัญก่อนสรุปชุดข้อมูล ไม่ได้ยืนยันว่ามีเพียงสามวันที่เสนอไว้
7. หนึ่งฤดูฝึกงานนับเป็นหนึ่งรอบของรายวิชา/โครงการ มีหลายใบสมัครและเปลี่ยนบริษัทได้โดยยังคงประวัติในฤดูเดิม ผู้ใช้ยืนยันว่ามีกรณีเปลี่ยนบริษัทจริง
8. เฟสนี้เน้นช่วงก่อนเริ่มฝึกงาน เรื่องระบบยศ/เลื่อนยศพักไว้ และยังไม่ออกแบบกลไกคะแนนในเฟสนี้
9. ปุ่มไอคอนล้วนบน Dashboard ทำให้ผู้ใช้ต้องเดาหน้าที่ ต้องปรับให้เข้าใจได้จากสิ่งที่แสดงบนหน้าจอ
10. เตรียมหลายฤดูฝึกงานพร้อมกันได้ แต่เลือกทำงานทีละฤดูบนหน้าจอ โดยต้องเห็นชัดว่าขณะนี้กำลังดูฤดูใด
11. เมื่อเพิ่มวันสำคัญ ให้เสนอการเตือนต่อทันที ผู้ใช้ปรับแล้วกดยืนยันได้ ไม่ต้องเริ่มตั้งเตือนใหม่เองอีกครั้ง ข้อเสนอเริ่มต้นคือก่อน 7 วันและ 1 วัน โดยยังต้องจัดการกรณีวันเตือนผ่านไปแล้วในการออกแบบรายละเอียด
12. ฤดูที่เลือกใช้ร่วมกันระหว่างเว็บกับ LINE และระบุชื่อฤดูในการ์ดยืนยันทุกครั้ง การ์ดที่เปิดค้างยังผูกกับฤดูต้นทางแม้ผู้ใช้สลับฤดูแล้ว
13. บัญชีที่มีข้อมูลเดิมได้ฤดูเริ่มต้นชื่อ “ฤดูฝึกงานเดิม” และข้อมูลเดิมย้ายเข้ารอบนี้ ผู้ใช้เปลี่ยนชื่อและเติมรายละเอียดภายหลังได้ โดยไม่เดาภาคเรียนหรือวันฝึกงาน
14. เมื่อเปลี่ยนวันสำคัญ ให้แสดงวันใหม่และรายการเตือนที่จะเลื่อนตาม แล้วผู้ใช้ตรวจและยืนยันด้วยกันครั้งเดียว การเตือนที่ส่งแล้วเก็บเป็นประวัติและไม่ส่งซ้ำ
15. แต่ละฤดูเก็บบริบทการศึกษาของรอบนั้น ฤดูใหม่ใช้โปรไฟล์ปัจจุบันเป็นค่าตั้งต้น การแก้โปรไฟล์ไม่เขียนทับฤดูที่มีอยู่ ผู้ใช้แก้ข้อมูลผิดของฤดูใดได้เฉพาะรอบนั้น
16. ข้อเสนอแนะระหว่างลอง Guided: แจ้งให้ชัดว่าถ้าไม่ได้เปลี่ยนสถาบัน ไม่จำเป็นต้องกรอกข้อมูลการศึกษาซ้ำ และหลังบันทึกวันสำคัญครั้งแรก ต้องเข้าถึงการเพิ่ม/แก้วันได้ง่ายกว่าการย้อนขั้นตอนตั้งค่า ต้นแบบเพิ่มปุ่มใช้ข้อมูลจากโปรไฟล์และหน้าภาพรวมฤดูเพื่อให้ลองแนวทางนี้ โดยยังไม่ได้เลือกแบบสุดท้าย

## ขอบเขตเฟสปัจจุบัน

- ข้อมูลนักศึกษา บริบทของฤดูฝึกงาน ประวัติแยกตามฤดู และการเตรียมตัวก่อนเริ่มฝึกงาน
- แบบข้อมูลต้องเก็บประวัติบริษัทหลายแห่งภายในฤดูเดียวได้ ส่วนขั้นตอนย้ายสถานที่ระหว่างฝึกงานจริงยังไม่ได้ตกลงให้พัฒนาในเฟสนี้
- ระบบยศและฟีเจอร์ระหว่าง/หลังฝึกงานอยู่ในขอบเขตภายหลัง

## การเลือกฤดูและการเตือนที่ตกลงแล้ว

- Dashboard ใบสมัคร เอกสาร เช็กลิสต์ และกำหนดการ ต้องแสดงขอบเขตของฤดูที่เลือก เพื่อไม่ให้ข้อมูลจากหลายฤดูปนกัน
- ผู้ใช้มีหลายฤดูที่กำลังเตรียมได้ การเลือกดูอีกฤดูไม่ใช่การปิดฤดูก่อนหน้า
- กำหนดการกับการเตือนเป็นคนละสิ่ง: บันทึกวันสำคัญก่อน แล้วเสนอการเตือนที่ปรับได้ และบันทึกการเตือนเมื่อผู้ใช้ยืนยัน
- การเสนอเตือนไม่ใช่หลักฐานว่าสร้างการเตือนสำเร็จ ต้องแสดงผลตามการบันทึกจริง
- ฤดูที่เลือกเป็นข้อมูลร่วมระดับบัญชี เว็บและ LINE ใช้ค่าเดียวกัน โดยการ์ดที่รอยืนยันต้องอ้างฤดูต้นทาง ไม่ย้ายตามค่าที่เลือกภายหลัง
- ข้อมูลเดิมที่ยังไม่มีฤดูจัดเข้า “ฤดูฝึกงานเดิม” ของเจ้าของบัญชีเดิม โดยรักษาข้อมูลและประวัติ ไม่สร้างปีการศึกษาหรือวันฝึกงานสมมติ

## ข้อเสนอแก้ความชัดเจนของปุ่ม Dashboard

แสดงชื่อที่มองเห็นได้สำหรับปุ่มด้านบน เช่น “ค้นหาฝึกงาน”, “ถามพี่ฝึกงาน”, “การแจ้งเตือน” แทนการพึ่งไอคอนหรือ tooltip เพียงอย่างเดียว
จอแคบควรจัดตำแหน่งหรือขึ้นแถวใหม่เพื่อรักษาชื่อปุ่ม ข้อเสนอนี้ยังอยู่ในร่าง ยังไม่ได้แก้ UI จริง

## ข้อสังเกตจากผู้ใช้เกี่ยวกับหน้าตัวอย่าง

- ต้องกำหนดชนิดช่องกรอกและชนิดข้อมูลจริงสำหรับมหาวิทยาลัย/คณะ/สาขา แทนค่าตัวอย่างที่เลือกไว้
- ประเภทการฝึกงานต้องเปิดให้ระบุประเภทอื่นได้ และยังไม่มีหลักฐานว่าชั่วโมง/สัปดาห์ตามตัวอย่างใช้กับทุกคน
- วันส่งใบตอบรับและสายงานที่สนใจก็ต้องมีวิธีตั้งค่าจริงเช่นกัน

| ข้อมูล | ช่องกรอก | รูปแบบข้อมูลที่เสนอ |
| --- | --- | --- |

ข้อมูลที่ยังไม่ทราบต้องแยกจากข้อมูลที่ไม่เกี่ยวข้องกับผู้ใช้ ห้ามใช้ 0 แทนชั่วโมงที่ยังไม่ทราบ
สาขาวิชาที่เรียนกับสายงานที่สนใจเป็นคนละข้อมูล เช่น เรียนสถิติแต่สนใจงาน UX Research

## ผลค้นคว้าเบื้องต้นและผลต่อข้อเสนอ

- คู่มือคณะวิศวกรรมศาสตร์ มหาวิทยาลัยพะเยาระบุ 240 ชั่วโมงสำหรับเครื่องกล/ไฟฟ้า/โยธา และ 270 ชั่วโมงสำหรับอุตสาหการในเอกสารเดียวกัน จึงใช้ 240 ชั่วโมงเป็นค่าเริ่มต้นสำหรับทุกคนไม่ได้ ไม่พบปีฉบับชัดเจน จึงใช้เป็นหลักฐานความแตกต่าง ไม่ใช่ข้อกำหนดปัจจุบันของนักศึกษารายใด ([คู่มือ](https://www.eng.up.ac.th/downloads/1646812442.pdf))
- ปฏิทินฝึกงานคณะบริหารธุรกิจและเทคโนโลยีสารสนเทศ มทร.ตะวันออก ปี 2569 แยกกำหนดการตามภาค/สาขา และมีขั้นตอนยื่นคำร้อง ส่งใบตอบรับ รับหนังสือส่งตัว ลงทะเบียน และเริ่ม/สิ้นสุดการฝึกงาน ข้อเสนอจึงเป็นรายการวันสำคัญที่เพิ่มได้ แทนการจำกัดไว้เพียงสามช่อง ([ปฏิทิน](https://busit.rmutto.ac.th/?page_id=6955))
- ข้อเสนอการรับเงื่อนไข: นักศึกษากรอกตามข้อมูลที่รู้ หรือส่งคู่มือ/ประกาศให้ AI อ่าน → ตรวจผลและแหล่งที่มา → ยืนยันก่อนใช้เป็นข้อมูลของฤดูฝึกงาน การยืนยันผล OCR ไม่เท่ากับการรับรองจากคณะ และคงป้าย AI_EXTRACTED ตามกติกาเดิม
- การเก็บแหล่งที่มาควรระบุหลักสูตร/รายวิชา/ปีการศึกษา/ภาคเรียนและฉบับเอกสารเท่าที่มี เพื่อป้องกันนำเงื่อนไขของคนละรอบมาใช้

## ประเด็นใหม่จากการแยกประวัติและระบบยศ

- ความหมายของฤดูฝึกงานตกลงแล้ว: หนึ่งรอบของรายวิชา/โครงการ เปลี่ยนบริษัทได้ในรอบเดิม
- ตกลงให้ฤดูเก็บบริบทการศึกษาของตนเอง การเปลี่ยนคณะ/ชั้นปีในโปรไฟล์ไม่เขียนทับรอบเดิม และแก้ข้อมูลผิดของฤดูได้โดยตรง
- เรื่องความก้าวหน้าที่ให้ยศและการสะสมข้ามรอบพักไว้ตามคำขอผู้ใช้
- ยศไม่ใช่ระดับความน่าเชื่อถือของข้อมูล และต้องไม่ทำให้ข้อมูล USER_REPORTED กลายเป็น SYSTEM_VERIFIED

## ข้อเท็จจริงจากระบบปัจจุบัน

- `worker/migrations/0001_init.sql` มี `users.profile_json` ค่าเริ่มต้น `{}` แต่ยังไม่มีฟังก์ชันอ่าน/แก้ไขโปรไฟล์สำหรับการใช้งานจริง
- `/api/state` ใน `worker/src/web-api.js` ส่งข้อมูลผู้ใช้เพียงอีเมลและสถานะผูก LINE
- `getOverview()` ใน `worker/src/store.js` ยังไม่ส่งข้อมูลโปรไฟล์ให้พี่ฝึกงาน
- หน้า `onboard` ใน `index.html` เป็นตัวอย่างและยังไม่บันทึกข้อมูล
- ใบสมัคร/เช็กลิสต์/เอกสาร/การเตือนผูกกับผู้ใช้โดยตรง ยังไม่มีการแบ่งฤดูฝึกงาน

## แนวทางพัฒนา (Approaches)

ข้อเสนอของผู้ช่วย: ใช้ Cloudflare Worker/D1 เดิม ข้อมูลส่วนตัวเก็บผ่าน `users.profile_json` ที่มีอยู่ ส่วนฤดูฝึกงานและวันสำคัญเป็นข้อมูลแยกตาราง แล้วเพิ่มขอบเขตฤดูให้ข้อมูลเดิม ทุกช่องทางเรียก service ชุดเดียวกัน

พิจารณาการเก็บฤดูทั้งหมดซ้อนใน `profile_json` แล้ว แต่ไม่เหมาะกับประวัติใบสมัคร/เอกสารที่มีอยู่แยกตาราง การกรองตามฤดูและ Cron จะต้องตามความสัมพันธ์ผ่าน JSON ซ้ำ จึงเลือกเสนอการแยกตารางเป็นแนวทางเดียวที่เหมาะกับขอบเขตที่ตกลง โดยยังไม่เพิ่มบริการหรือฐานข้อมูลใหม่ การเลือกทางเทคนิคนี้เป็นข้อเสนอของผู้ช่วย ไม่ใช่คำตอบที่ผู้ใช้เลือกไว้ระหว่างสัมภาษณ์

## แบบข้อมูลที่เสนอ

- **Profile:** ชื่อที่อยากให้เรียก บริบทการศึกษาปัจจุบัน ชั้นปี สายงานที่สนใจ พร้อม version และเวลาแก้ไข อีเมลเข้าสู่ระบบ/สถานะ LINE เป็นข้อมูลบัญชีเดิม ไม่ให้แก้ผ่านฟอร์มนี้
- **Season:** id, user_id, ชื่อที่ผู้ใช้ตั้ง, บริบทการศึกษาที่คัดลอกจากโปรไฟล์ตอนสร้าง, ประเภทรวมชื่อประเภทอื่น, รายวิชา/โครงการ, ปี/ภาคเรียน, วันเริ่ม/สิ้นสุดที่ยังไม่ทราบได้, ข้อกำหนดระยะเวลาพร้อมเงื่อนไขต้นฉบับและแหล่งที่มา, version และเวลาแก้ไข ทุกช่องนอกจากชื่อเว้นได้; ชื่อเริ่มต้นสำหรับผู้ใช้ใหม่คือ “ฤดูฝึกงานของฉัน” ที่แก้ได้ ไม่ใช่ปี/เทอมสมมติ
- **Selected season:** เก็บ id ระดับบัญชี ไม่ผูกกับ browser storage และตรวจว่าเป็นของผู้ใช้จริงเสมอ
- **Milestone:** id, user_id, season_id, ชื่อกำหนดการ, วันเดียวหรือช่วงวัน, สถานะข้อมูล unknown/known/not_applicable, provenance และ version วันเริ่ม/สิ้นสุดที่อยู่ใน Season ใช้เป็นเหตุการณ์ต้นทางโดยไม่สร้างสำเนาวันที่ที่แก้แยกแล้วขัดกัน
- **Reminder:** เพิ่ม season_id และ milestone reference ที่เว้นได้ เพราะการเตือนทั่วไปยังมีอยู่ เก็บระยะก่อนเหตุการณ์/เวลาแจ้งเตือนสำหรับรายการที่เลื่อนตามวันสำคัญได้; เวลาเป็น UTC และแสดง/รับค่าตาม Asia/Bangkok
- **Pending action:** id แบบทึบ, เจ้าของ, season_id ต้นทาง, ชนิดคำสั่ง, payload, expected versions, สถานะและหมดอายุ ใช้รองรับการยืนยันทั้งเว็บ/LINE โดยไม่เชื่อ season_id หรือค่าที่ส่งกลับจาก client เพียงอย่างเดียว
- เพิ่ม season_id ให้ applications, tasks, documents, reminders, messages และ extractions รวมถึง audit records ใหม่; ข้อมูลเก่าใน audit ยังคง payload/เวลาเดิม ไม่เขียนประวัติขึ้นใหม่
- โปรไฟล์/ค่าฤดู/วันสำคัญเก็บ provenance ระดับฟิลด์หรือกลุ่มที่แก้พร้อมกัน: วิธีได้มา, truth_level, เอกสาร/URL/หน้า/ขอบเขตหลักสูตร/ปีเท่าที่รู้ ผู้ใช้แก้ฟิลด์ที่ AI อ่านเองจะเป็น USER_REPORTED เฉพาะฟิลด์ที่แก้ พร้อมเก็บประวัติเดิม
- ไม่ใช้ชื่อบริษัทเป็นกุญแจของฤดู การจับคู่ชื่อ/ตรวจรายการซ้ำต้องจำกัด user_id + season_id บริษัทเดียวกันอยู่คนละฤดูได้

รายละเอียดชื่อคอลัมน์ ดัชนี ข้อจำกัดความยาว และ migration SQL เป็นหน้าที่ผู้พัฒนา โดยต้องรักษาความหมายและเงื่อนไขในแบบนี้

## ขั้นตอนใช้งาน

1. ผู้ใช้เริ่มใช้ได้เลย ไม่บังคับ onboarding; เมื่อจำเป็นจึงถามข้อมูลที่ขาดและยอมให้ตอบว่ายังไม่ทราบ
2. บนเว็บมีตัวเลือกฤดูที่อ่านชื่อได้ชัด; LINE มีคำสั่ง/การ์ดดู สร้าง และสลับฤดู ค่าที่เลือกใช้ร่วมกัน คำตอบที่มีการเปลี่ยนข้อมูลต้องมีชื่อฤดู
3. หน้าตั้งค่าแบ่งข้อมูลส่วนตัวกับข้อมูลฤดูที่เลือก การ์ด Dashboard แสดงชื่อที่อยากให้เรียก (ใช้อีเมลหากยังไม่กรอก) และบริบทการศึกษาของฤดูที่เลือก ไม่เอาโปรไฟล์ปัจจุบันไปเขียนทับประวัติ
4. แบบฟอร์มบนเว็บแสดงค่าที่เปลี่ยนให้ตรวจและบันทึก; แชทตีความคำขอแก้โปรไฟล์/ฤดูเป็นข้อเสนอพร้อมการ์ดยืนยัน ไม่แก้ข้อมูลจากการคุยทั่วไปอย่างเงียบ ๆ
5. ส่งคู่มือ/ประกาศให้ OCR ได้จากทั้งสองช่องทาง ผลยัง pending มีป้าย AI_EXTRACTED ให้ตรวจแต่ละฟิลด์/เลือกใช้ แล้วจึงยืนยัน เงื่อนไขที่ขัดกับของเดิมแสดงก่อน–หลัง ไม่ถือว่าข้อความล่าสุดหรือผล AI ถูกกว่าโดยอัตโนมัติ
6. ยืนยันวันสำคัญแล้วส่งการ์ดเสนอเตือนต่อทันที โดยยังไม่สร้างการเตือน ให้ปรับหรือเลือกไม่ตั้งได้
7. ค่าเสนอเริ่มต้นของผู้ช่วย: ก่อน 7 วันและ 1 วัน เวลา 09:00 ไทย เสนอเฉพาะเวลาในอนาคต ถ้าไม่เหลือช่วงเสนอให้เลือกเวลาใหม่เอง ไม่ส่งเตือนย้อนหลัง วันที่ยังไม่ทราบจะบันทึกเป็นร่างโดยไม่สร้างเตือน
8. เมื่อเปลี่ยนวันสำคัญ แสดงวันใหม่และการเตือนที่ผูกไว้ซึ่งยังไม่ส่ง ให้ปรับและยืนยันชุดเดียวกัน แล้วบันทึกวันสำคัญ/การเตือน/ประวัติแบบ atomic การเตือนที่ส่งแล้วและการเตือนทั่วไปที่ไม่ได้ผูกกำหนดการไม่ถูกเลื่อน
9. พี่ฝึกงานอ่านโปรไฟล์ที่จำเป็น + บริบทและประวัติสนทนาของฤดูต้นทาง ไม่ดึงข้อมูลทุกฤดูมาปน คำขอที่ระบุชื่อฤดูคลุมเครือให้ถามก่อนทำรายการ

## กติกาการทำงานร่วมกันและการยืนยัน

- จับฤดูต้นทางตอนเริ่มคำขอ แชท/OCR/ฟอร์ม และใช้ค่านี้จนจบคำขอ แม้ผู้ใช้สลับฤดูระหว่างรอผล
- เว็บส่ง season reference ที่แสดงอยู่และ expected selection/version มาด้วย ถ้าบัญชีเปลี่ยนฤดูจากอีกช่องทางแล้ว ให้แจ้งและรีโหลดก่อนเริ่มคำสั่งใหม่ ไม่บันทึกเงียบ ๆ ลงฤดูที่หน้าจอไม่ได้แสดง
- การกดยืนยันจากการ์ดค้างทำรายการกับฤดูที่แสดงบนการ์ด ไม่สลับฤดูปัจจุบันตามเอง กดซ้ำ/LINE redelivery ต้องไม่สร้างข้อมูลหรือการเตือนซ้ำ
- การ์ดยืนยันมีอายุ 24 ชั่วโมงตามข้อเสนอผู้ช่วย; เมื่อข้อมูลต้นทางเปลี่ยน version ให้แจ้งว่ามีข้อมูลใหม่และเสนอการ์ดใหม่ ไม่เขียนทับด้วยค่าจากการ์ดเก่า
- ทุก mutation และ audit ต้องบันทึกสำเร็จด้วยกัน บอกว่าสำเร็จเมื่อฐานข้อมูลยืนยันแล้ว การเรียกโมเดลล้มหลังบันทึกให้คงพฤติกรรม partial success ที่มีอยู่
- ขณะเลื่อนวันสำคัญ Cron กับคำสั่งแก้เตือนต้อง claim/ตรวจรุ่นรายการอย่างสอดคล้องกัน รายการที่เริ่มส่งก่อนยืนยันการแก้ถือเป็นประวัติที่ส่งแล้วและแจ้งในผลยืนยัน ไม่สร้างซ้ำ หากแก้สำเร็จก่อน claim จะส่งตามเวลาใหม่
- เตือนที่ยืนยันไว้ทำงานจากทุกฤดู ไม่ขึ้นกับฤดูที่เลือกดู การ์ดเตือนและแบนเนอร์ระบุชื่อฤดูและเปิดไปยังรายการต้นทางได้ LINE ส่งไม่สำเร็จคงมี fallback บนเว็บ; เว็บมีจำนวนรายการค้างทุกฤดูเพื่อไม่ให้ซ่อนรายการที่ต้องรับรู้

## ประวัติและขอบเขตเฟส

ค่าเสนอของผู้ช่วย: รอบแรกเก็บทุกฤดูไว้และสลับกลับมาดู/แก้ได้พร้อม audit โดยยังไม่เพิ่มระบบปิดฤดู ลบฤดู หรือย้ายข้อมูลข้ามฤดู การแยกประวัติหมายถึงไม่ปนกันและไม่เขียนทับอัตโนมัติ ไม่ได้หมายถึงข้อมูลเก่าแก้ไม่ได้

เช็กลิสต์ตั้งต้นยังเป็นทั่วไป ไม่รับรองว่าตรงกับคณะ เมื่อใช้คู่มือให้สร้าง/ปรับรายการที่ผู้ใช้ตรวจและยืนยันพร้อมแหล่งที่มา ไม่เปลี่ยนขั้นตอนสำเร็จของเดิมโดยเงียบ ๆ

หน้าค้นหาและงานที่กดดาวยังเป็นประกาศตัวอย่างตามระบบเดิม ไม่เพิ่มแหล่งงานจริงในงานนี้ รายการดาวที่อยู่ในหน่วยความจำเว็บต้องแยกตามฤดูและล้างข้ามบัญชี; ไม่อ้างว่า sync กับ LINE หรือเก็บถาวร ส่วนรายการ Saved ในบอร์ดจริงเก็บฝั่ง Worker ตามฤดู

พักระบบยศ ฟีเจอร์ขณะฝึกงาน/หลังฝึกงาน ฐานกฎทุกคณะ และการทำ Admin ไว้ตามขอบเขตเดิม

## การย้ายข้อมูลและการนำขึ้นใช้งาน

- migration เพิ่มฤดูเริ่มต้น “ฤดูฝึกงานเดิม” สำหรับผู้ใช้ที่มีข้อมูลอยู่ แล้วผูกข้อมูลเดิมครบ รวมข้อความ ผล OCR pending และการเตือน ห้ามเปลี่ยน id, สถานะ, sent_at, due_at หรือเวลาประวัติเดิม ไม่มีการแจ้งเตือน/อีเมลระหว่าง migration
- เลือกฤดูเริ่มต้นของแต่ละบัญชี แล้วตรวจจำนวนข้อมูลก่อน/หลังและไม่เหลือข้อมูลฤดูที่กำกวม สำหรับผู้ใช้ใหม่สร้างฤดูว่างแบบทำซ้ำได้ปลอดภัยโดยไม่บังคับกรอกโปรไฟล์
- การ์ดเก่าอ้าง entity id ให้หาเจ้าของ/ฤดูจากข้อมูลที่ย้ายแล้ว ส่วน menu เก่าที่ไม่มี entity ใช้ฤดูที่เลือก กรณีระบุเป้าหมายแน่นอนไม่ได้ให้ขอทำรายการใหม่ ห้ามเดา
- migration กับ Worker ต้องมีแผน rollout ที่ Cron รุ่นเก่าไม่ส่งการเตือนที่กำลังย้าย; งด Cron ชั่วคราวตามวิธีที่ตรวจสอบได้ระหว่างเปลี่ยนรุ่น และเปิดคืนหลัง smoke check
- ไม่อ้างว่า backend ถูก deploy ตาม GitHub Pages: แยกตรวจ Worker/D1 และเว็บจริง มีสำรองข้อมูลก่อน production migration; ห้ามทดสอบด้วยการส่งข้อความจริงให้ผู้ใช้โดยไม่อยู่ในขอบเขตที่อนุญาต

## Shared backend และสัญญา API

เพิ่ม service กลางสำหรับ profile, seasons, milestones และ confirmation proposals ให้ Web API, assistant tools และ LINE เรียกชุดเดียวกัน; card object กลางใน cards.js, แปลง Flex ใน flex.js, renderCard บนเว็บ และ runCardAction เป็นทางยืนยันกลางตามเดิม

API ต้องมีการอ่าน/แก้โปรไฟล์, อ่าน/สร้าง/แก้/เลือกฤดู, อ่าน/สร้าง/แก้วันสำคัญ และการเสนอ/ยืนยันการเตือน โดย /api/state คืนข้อมูลฤดูที่เลือกพร้อมรายการฤดูและ profile ที่จำเป็น Endpoints และชื่อ tools เป็นรายละเอียดที่ผู้พัฒนากำหนดได้ แต่ทุก query/mutation ตรวจเจ้าของและขอบเขตฤดูที่ฝั่ง Worker ไม่เชื่อ id จาก AI/client

คำสั่งเดิมทั้งหมดต้องอยู่ในขอบเขตฤดูที่จับไว้ รวม get_overview, ค้นหาใบสมัครจากชื่อ, set_task, ลบการเตือนจาก keyword, OCR confirm และสรุปจาก rich menu

## เกณฑ์ตรวจรับ

1. ผู้ใช้ใหม่เริ่มบันทึกใบสมัครได้โดยโปรไฟล์ยังว่าง ไม่มีมหาวิทยาลัย ชั่วโมง วัน หรือสายงานตัวอย่างถูกบันทึกให้อัตโนมัติ
2. กรอก/แก้โปรไฟล์และข้อมูลฤดูผ่านเว็บกับ LINE ได้ ใช้ service/cards/actions ชุดเดียวกัน และ audit ระบุ channel/truth ถูกต้อง
3. สองฤดูมีบริษัทชื่อเดียวกันได้ การแก้สถานะ/เอกสาร/เช็กลิสต์/OCR/ลบเตือนในฤดูหนึ่งไม่กระทบอีกฤดู และไม่อ่านข้อมูลบัญชีอื่น
4. สลับฤดูจากเว็บแล้ว LINE ใช้ฤดูเดียวกัน เว็บที่ค้างแสดงฤดูเก่าต้องไม่เขียนลงฤดูใหม่แบบเงียบ ๆ
5. การ์ดค้าง/OCR ที่กำลังอ่านยังบันทึกลงฤดูต้นทางหลังสลับฤดู; replay, version เก่า และการ์ดของบัญชีอื่นถูกจัดการโดยไม่สร้างข้อมูลผิดหรือซ้ำ
6. แก้โปรไฟล์เป็นปี 4 แล้วฤดูเก่าที่เป็นปี 3 ยังอยู่เหมือนเดิม แก้รอบเก่าได้เฉพาะเมื่อผู้ใช้สั่งแก้รอบนั้นจริง
7. บันทึกวันสำคัญแล้วได้รับข้อเสนอเตือนทันที ยังไม่มี reminder จนยืนยัน ปรับเวลา/ไม่ตั้งได้ และไม่เสนอเวลาในอดีต
8. เลื่อนวันสำคัญพร้อมการเตือนในคำยืนยันเดียว รักษารายการที่ส่งแล้ว กดซ้ำไม่สร้างซ้ำ และมีเทสต์กรณีแข่งกับ Cron
9. Cron ส่งรายการจากฤดูที่ไม่ได้เลือกอยู่ได้ พร้อมชื่อฤดู LINE ล้มเหลวเห็น fallback และรายการค้างข้ามฤดูบนเว็บ
10. migration ทำซ้ำได้อย่างปลอดภัยหรือมี migration guard รักษาจำนวน/id/ประวัติข้อมูลเดิมครบ และการ์ดเก่าไม่ถูกโยนไปฤดูอื่น
11. ปุ่ม Dashboard อ่านชื่อได้ที่ desktop/mobile จอแคบไม่ย้อนกลับเป็นไอคอนล้วน ช่องกรอกไม่มีค่าตัวอย่างที่ถูกอ้างเป็นข้อมูลจริง และ UI บอกกรณีไม่ทราบ/ยังไม่บันทึก/ผิดพลาดตรงกับฐานข้อมูล
12. ก่อนรายงานพัฒนาเสร็จ รัน backend suite ทั้งหมดและ syntax check ตาม AGENTS.md รีเฟรช Index ตรวจ browser จริงทั้งจอกว้าง/มือถือ commit/push และตรวจ Pages กับ Worker/D1 แยกกัน

## ข้อจำกัดจากสถาปัตยกรรมเดิม

- LINE และเว็บใช้ตรรกะและข้อมูลชุดเดียวกัน โดย LINE เป็นช่องทางหลัก
- ข้อมูลที่นักศึกษากรอกเองใช้ `USER_REPORTED` และมีประวัติการแก้ไข
- ข้อมูลที่ AI อ่านต้องให้ผู้ใช้ตรวจและยืนยันก่อนบันทึกตามกติกาเดิม
- ห้ามแสดงข้อมูลที่ผู้ใช้ยังไม่ได้ให้เป็นข้อเท็จจริง หรือถือว่าชื่อคณะเป็นหลักฐานยืนยันข้อกำหนดคณะ

ข้อเสนอทางเทคนิคและค่าเริ่มต้นที่ผู้ช่วยกำหนดในเอกสารนี้ต้องตรวจรวมกับข้อตกลงผลิตภัณฑ์ก่อนเริ่มพัฒนา ยังไม่มี product code หรือ production data เปลี่ยนจากงานออกแบบนี้

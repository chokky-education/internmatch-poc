# InternMatch Prototype: LINE OA หลัก, เว็บสำรอง (Design)

วันที่: 2026-11-11 · สถานะ: รออนุมัติ

## 1. เจตนา (Why)
นักศึกษาคุยกับ "พี่ฝึกงาน" ผ่าน LINE OA เป็นช่องทางหลัก เจ้าของโปรเจกต์เคยเจอ LINE Messaging API ล่มจนบริการแชทของตัวเองใช้ไม่ได้ จึงต้องมี **เว็บที่ทำได้ทุกอย่างเท่ากับ LINE** ไว้ใช้ตอน LINE ล่ม รอบนี้ต้องการ **prototype ที่ใช้งานจริง** ให้ทุกคนในทีมลองใช้ได้ (เพิ่มเพื่อน OA แล้วคุยได้จริง)

## 2. เป้าหมาย / ไม่ทำ / ถือว่าล้มเหลว
**เป้าหมาย**
- คุยกับพี่ฝึกงานใน LINE OA จริงได้ทั้งพิมพ์และส่งรูป (OCR) และบอทจัดการข้อมูลผ่าน function calling ชุดเดิม
- เว็บทำทุกอย่างที่ LINE ทำได้ (แชทกับพี่ฝึกงาน, อัปรูปให้ OCR, จัดการบอร์ด/เช็กลิสต์/เตือน) บนข้อมูลชุดเดียวกัน
- การเตือนส่งไปทาง LINE และแสดงบนเว็บด้วยเสมอ

**ไม่ทำในรอบนี้**
- ไม่มีส่วนอาจารย์/Admin/Approval เลย (ลบหน้า `pipeline` ออก และไม่มีบทบาท admin ในระบบ)
- ไม่ทำแชทกลุ่มเพื่อน, ไม่ทำค้นหาประกาศงานจากแหล่งภายนอก (หน้า discover ใช้ข้อมูลตัวอย่างต่อได้)
- ไม่มีระบบตรวจสถานะ LINE อัตโนมัติ (การประกาศย้ายไปเว็บทำผ่านโซเชียลมีเดียของแพลตฟอร์มด้วยมือ)

**ถือว่าล้มเหลวถ้า**
- LINE ล่มแล้วนักศึกษาเข้าเว็บไม่ได้ หรือเว็บทำบางอย่างไม่ได้
- ข้อมูลที่ทำใน LINE ไม่เห็นบนเว็บ หรือกลับกัน
- มี API key/secret อยู่ใน Git หรือในโค้ดฝั่งเบราว์เซอร์

## 3. ข้อจำกัด
- เจ้าของมี LINE OA, บัญชี Cloudflare และ `wrangler` CLI แล้ว
- เว็บเดิมเป็น `index.html` ไฟล์เดียวบน GitHub Pages
- Truth Hierarchy (SYSTEM_VERIFIED / USER_REPORTED / AI_EXTRACTED) ต้องคงอยู่ทุกช่องทาง รวมถึงข้อความใน LINE (AI_EXTRACTED ต้องให้ผู้ใช้ยืนยันก่อนบันทึก)
- ผู้ใช้คือทีม (หลักสิบคน) ใช้ free tier ได้

## 4. สิ่งที่ตัดสินใจแล้ว
**จากเจ้าของโปรเจกต์**
- LINE หลัก เว็บเป็นช่องทางสำรองที่ความสามารถเท่ากัน
- เว็บล็อกอินด้วยอีเมลมหาวิทยาลัยได้ **โดยไม่พึ่ง LINE** (LINE Login ห้ามเป็นทางเดียว)
- การแจ้งนักศึกษาตอน LINE ล่มใช้โซเชียลมีเดียของแพลตฟอร์ม
- เป็น prototype จริง ทีมใช้ได้ ไม่มีส่วนอาจารย์
- **ช่วง prototype ล็อกอินได้เฉพาะอีเมลใน allowlist (ทีม 4 คน)** ทั้งทางเว็บและการผูก LINE; อีเมลอื่นไม่ได้รับ OTP และบอทตอบว่ายังไม่เปิดให้ใช้
  - รายชื่ออีเมลเก็บเป็น Worker secret/env (`ALLOWED_EMAILS`) **ห้าม commit ลง repo** เพราะ repo เป็นสาธารณะ

**การตัดสินใจของ Claude (เปลี่ยนได้)**
- **Backend:** Cloudflare Worker ตัวเดียว + D1 (SQLite) + R2 สำหรับรูปที่อัปโหลด ถ้าจำเป็น
- **สถาปัตยกรรม:** "ตัวกลางเดียว สองหน้าบ้าน" — logic ทั้งหมด (บอท Gemini + tools, Paxa OCR, กฎ Truth Hierarchy, audit trail) อยู่ใน Worker; LINE webhook และ Web API เรียกฟังก์ชันชุดเดียวกัน ห้ามมี logic ซ้ำในเบราว์เซอร์
- **ตัวตน:** 1 คน = 1 บัญชีที่ผูกกับอีเมล
  - เว็บ: ใส่อีเมล → รับรหัส OTP 6 หลักทางอีเมล → session cookie
  - LINE: ครั้งแรกที่ทัก บอทขออีเมล → ส่ง OTP ไปอีเมล → พิมพ์ OTP ใน LINE → ผูก `line_user_id` กับบัญชี
- **ส่งอีเมล:** เจ้าของไม่มีโดเมน → ใช้ **Brevo** (HTTP API, free 300 ฉบับ/วัน) ด้วยการยืนยันอีเมลผู้ส่งเดี่ยว (Gmail ของเจ้าของ) ไม่ต้องมีโดเมน; Resend ใช้ไม่ได้เพราะถ้าไม่มีโดเมนจะส่งได้แค่ถึงอีเมลตัวเอง
  - ความเสี่ยง: อีเมลอาจเข้า spam → หน้าล็อกอินต้องบอกให้เช็ก spam; ถ้ามีโดเมนภายหลังค่อยย้าย
  - ทางหนีไฟระหว่าง prototype: ถ้าอีเมลส่งไม่ถึง เจ้าของออก OTP ให้ด้วย `wrangler` (สคริปต์เล็กๆ) แล้วแจ้งเองได้
- **Secrets:** LINE channel secret/access token, Gemini key, Paxa key เก็บเป็น Worker secrets (`wrangler secret put`) เท่านั้น เลิกใช้ localStorage/URL param สำหรับ key
- **เว็บ:** ต่อยอด `index.html` เดิม (ยังอยู่บน GitHub Pages) ให้อ่าน/เขียนผ่าน Worker API แทน state ในเบราว์เซอร์; แชท drawer "พี่ฝึกงาน" บนเว็บเรียก endpoint เดียวกับ LINE
- **การเตือน:** Cron Trigger ของ Worker ตรวจทุก 15 นาที แล้ว push ทาง LINE; ถ้าส่งไม่สำเร็จ ให้บันทึกไว้และแสดงบนเว็บเป็น "เตือนที่ยังไม่ได้อ่าน"
- **กันข้อมูลซ้ำหลัง LINE กลับมา:** เก็บ `webhookEventId` ไว้ตัดเหตุการณ์ซ้ำ; ทุกการเปลี่ยนข้อมูลบันทึก `channel` (line/web) ใน audit trail
- **หน้าจอ:** ลบ `pipeline` และส่วน Admin; เปลี่ยนหน้า `chat` (LINE จำลอง) เป็นแชทจริงบนเว็บ + แสดงประวัติบทสนทนาที่คุยใน LINE ด้วย (บทสนทนาเก็บใน D1 รวมสองช่องทาง)

- **AI:** โค้ดเดิมเรียก Paxa (`api.paxalabs.com`) และ Gemini API จริงอยู่แล้ว ใช้ต่อ; ชื่อโมเดลเป็นค่า env ไม่ hardcode
- **OCR scope:** โพสต์งานทำครบ end-to-end (ยืนยัน → การ์ดบนบอร์ด) ทั้ง LINE และเว็บ; อีก 3 ชนิด (คู่มือคณะ, ใบเกรด, หนังสือตอบรับ) อ่าน + ยืนยันได้ แต่บันทึกเข้าคลังเอกสารเท่านั้น

## 5. ข้อมูลหลัก (ร่าง)
`users(id, email, line_user_id?, profile_json)`, `applications`, `tasks` (เช็กลิสต์คณะ), `documents`, `reminders(due_at, sent_at, channel_result)`, `messages(user_id, channel, role, content, created_at)`, `audit_log(user_id, entity, change, channel, truth_level, at)`, `otp`, `sessions`, `line_events(webhook_event_id)` — ทุกแถวที่แสดงบน UI มี `truth_level`

## 6. สิ่งที่เจ้าของต้องทำเอง (Claude จะให้ขั้นตอนละเอียดตอนถึง)
1. LINE Developers Console: เปิด Messaging API, ให้ Channel secret + access token, ตั้ง Webhook URL ที่ได้จาก Worker, เปิด "Use webhook", ปิด auto-reply
2. ให้ Gemini API key และ Paxa key
3. สมัคร Brevo (ฟรี) ยืนยัน Gmail ผู้ส่ง แล้วให้ API key
4. แจก QR ของ OA ให้ทีม

## 7. ปล่อยให้ builder ตัดสิน
- โครงสร้างโค้ด Worker, router, ไลบรารี, schema ละเอียด
- รูปแบบข้อความ LINE (ข้อความธรรมดา vs Flex/Quick Reply) ขอแค่ให้มีปุ่มยืนยันผล AI_EXTRACTED
- Rich menu ของ OA (ถ้ามีเวลา)
- CORS/session รายละเอียด ระหว่าง GitHub Pages กับ Worker
- อัปเดต `AGENTS.md`, `INDEX.md`, `PRD.md` ให้สะท้อนสถาปัตยกรรมใหม่ (LINE หลัก / เว็บ parity / ไม่มี admin)

## 8. การตรวจรับ
- ทีมเพิ่มเพื่อน OA → ผูกอีเมล → พิมพ์ "สมัคร SCB ตำแหน่ง Data intern แล้ว" → การ์ดขึ้นบนเว็บเป็น USER_REPORTED
- ส่งรูปโพสต์งานใน LINE → บอทตอบผลพร้อมป้าย AI_EXTRACTED และปุ่มยืนยัน → ยืนยันแล้วเห็นบนเว็บ
- ปิด webhook ใน LINE Console (จำลองล่ม) → ล็อกอินเว็บด้วยอีเมล → ทำทุกขั้นข้างบนบนเว็บได้ครบ → เปิด webhook กลับ → LINE เห็นข้อมูลเดียวกัน
- ตั้งเตือน → ได้ push ใน LINE และเห็นบนเว็บ
- `git grep` ไม่พบ key ใดๆ
